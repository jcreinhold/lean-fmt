# stream request cost — RSF-FINAL
#
# What a one-shot stdin request costs, and specifically whether asking for a *range* costs less than
# asking for the whole buffer. It does not, and that is the finding: the cost of a stream request is
# one exact frontend run over the whole buffer, which a range cannot avoid without giving up exactness
# (a range must never slice bytes and parse them as a module). Range formatting is a precision
# feature — which bytes come back changed — not a speed feature, and nothing in the product or its
# documentation may imply otherwise.
#
# Measured with /usr/bin/time -p, three runs each, on this repository, LEAN_NUM_THREADS unset.
# `lake exe` process overhead is measured separately and is included in every figure below.

lake exe overhead (`lean-fmt --version`)     real 0.46  0.42  0.44

LeanFmt/Doc.lean — 13,897 bytes
  stdin, whole buffer                        real 1.95  1.55  1.65
  stdin, one-unit range (200:260)            real 1.59  1.58  1.56
  batch `format --check FILE`, cache cleared real 1.80  1.68  1.70

LeanFmt/Application.lean — 96,341 bytes
  stdin, whole buffer                        real 4.06  4.04  4.60
  stdin, one-unit range (200:260)            real 5.38  4.38  4.11

Reading:

- A range costs what the whole buffer costs. The spread between the two rows is inside the run-to-run
  spread of either one.
- A stream request costs about what the batch path costs for the same single file with the cache
  cleared (1.6s against 1.7s on Doc.lean). `loadWorkspaceOnly` buys back what a one-file batch run
  spends selecting the project; it does not make the frontend cheaper, because nothing does.
- Net of the 0.44s `lake exe` overhead, 13.9 KB costs ~1.1s and 96 KB ~3.6s — 6.9× the bytes for 3.2×
  the time. The work is elaboration, not layout, so it tracks what the module declares rather than how
  long it is.
